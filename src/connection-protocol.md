# Team Solve connection protocol

Version 1, implemented by the Streamer.bot prototype. This fills in the connection messages left unspecified by the [action protocol](puzzle-command-protocol.md). The userscript must implement this contract. All messages are JSON objects with `type` and integer `version: 1`. Identifiers are nonempty opaque strings. Wire names are case-sensitive.

## Selecting a browser

Opening a socket does not enable contributions. On explicit enablement, the browser opens a new connection and sends:

```json
{"type":"sessionActivate","version":1,"requestId":"attempt-1","puzzleId":"puzzle-instance-1"}
```

Streamer.bot revokes the previous selection locally, completes its pending actions without retry, sends `sessionClose` to the previous connected browser, and closes that socket. It accepts the new browser with:

```json
{"type":"sessionAccepted","version":1,"requestId":"attempt-1","selectionId":"selection-1","sessionId":"session-1","puzzleId":"puzzle-instance-1"}
```

`requestId` echoes the activation or resume attempt. `selectionId` is generated by Streamer.bot and retained by the browser for transient reconnection. `sessionId` is generated anew on every acceptance. Both are independent of the host's socket ID. Do not log selection IDs: they represent resume eligibility.

Each explicit activation uses a new socket. An accepted browser starts unready, regardless of its previous state. It must send fresh readiness after acceptance. A puzzle load/reload creates a new puzzle instance ID and disables the browser switch, as required by the action protocol.

If acceptance is lost with the connection, a browser without an accepted selection must require explicit enablement again; it must not automatically issue new activation requests that could replace another tab.

## Readiness and heartbeat

```json
{"type":"readiness","version":1,"sessionId":"session-1","puzzleId":"puzzle-instance-1","ready":true}
```

Only the accepted socket and matching session/puzzle can update readiness. `false` pauses contributions and closes pending actions as uncertain without retry. Readiness alone cannot select a browser.

Streamer.bot periodically sends:

```json
{"type":"heartbeat","version":1,"requestId":"heartbeat-1","sessionId":"session-1","puzzleId":"puzzle-instance-1"}
```

The browser promptly returns current readiness without waiting for its action queue:

```json
{"type":"heartbeatReply","version":1,"requestId":"heartbeat-1","sessionId":"session-1","puzzleId":"puzzle-instance-1","ready":true}
```

Replies must match the outstanding heartbeat as well as socket, session, and puzzle. The first heartbeat is due immediately after acceptance. Later ones are due five seconds after a matched reply. Ten seconds without a matched reply disconnects the session, preserving only selection eligibility for resume. Late replies cannot restore it.

## Resume, release, and replacement

After transient disconnection, the same enabled puzzle may reconnect and send:

```json
{"type":"sessionResume","version":1,"requestId":"attempt-2","selectionId":"selection-1","puzzleId":"puzzle-instance-1"}
```

Resume succeeds only if that selection is still current, its puzzle matches, and its previous socket is no longer attached. Success returns `sessionAccepted` with the same selection ID, a fresh session ID, and the new request ID. It requires fresh readiness. The browser never resends puzzle actions or acknowledgements after reconnecting.

A rejected resume receives the following response and its socket is closed. The browser disables its switch and requires explicit enablement:

```json
{"type":"sessionRejected","version":1,"requestId":"attempt-2","reason":"resumeRejected"}
```

On browser disablement, prevent local execution immediately, send this release if connected, and close the socket:

```json
{"type":"sessionRelease","version":1,"selectionId":"selection-1","sessionId":"session-1","puzzleId":"puzzle-instance-1"}
```

A matching release forgets the selection, pauses contributions, closes pending actions, and closes the socket. A stale release does nothing. If delivery is lost, the disabled browser still must not reconnect; the server cannot distinguish an undelivered release from transient loss until a future explicit activation replaces it.

Replacement sends the old browser:

```json
{"type":"sessionClose","version":1,"sessionId":"session-1","puzzleId":"puzzle-instance-1","reason":"replaced"}
```

The browser disables itself, discards queued actions, and cancels automatic reconnection. Revocation does not depend on successful delivery. A replaced browser's resume cannot replace the new selection.

Neither activation, readiness, release, nor disconnect modifies Streamer.bot's saved enabled state or access policy. Streamer.bot restart discards all selection eligibility; an old resume is rejected and the browser must be explicitly enabled again.

## Validation and failures

Malformed JSON, unknown types, unsupported versions, missing correlation identifiers, and wrong field types are logged and ignored. Connection messages do not receive action acknowledgements. Action acknowledgements follow the separate action protocol; Streamer.bot retains any nonempty browser failure `reason` as diagnostic data, including future reason codes.

The host's send method returns no delivery result. A thrown send failure marks the current session unavailable; otherwise acknowledgement deadlines and heartbeats establish failure. No successful send alone proves execution. The only automatic repetition is heartbeat traffic, never puzzle actions.
